"effect": minor
---

Add encrypted remote compaction groundwork to the event log. `EventLog.groupCompaction`, `EventLog.groupBatchCompaction` and `Registry.registerCompaction` take a `remote` option that opts a compactor into building snapshots of a remote's history, and `Registry.compactors` values carry `remote`. `EventRow.compaction` is opted in. A remote compaction only drops entries: a call that writes a new entry keeps its whole input, and entries that fail to decode, including entries with fields the schema does not know, are always kept.

`EventLogServerEncrypted.Storage` gains an optional `compaction` member with the storage primitives for encrypted remote compaction: status, begin, input headers, fetch, staged parts, commit, no-op recording, abort, rollback and history. A rollback reactivates the previous generation and appends the input of the withdrawn snapshot's stage at the head, at sequences taken as writes take them, so every client, including ones from before remote compaction, receives the entries the snapshot dropped through `changes`. `makeCompactionConfig` resolves the shared tuning (grace, lag, stage TTL, threshold floor and sweep interval) and rejects a grace that isn't longer than the lag and the stage TTL. The memory storage always provides `compaction`, serves an active snapshot through `changes`, and prunes superseded generations after the grace period. `makeStorageMemoryWith` and `layerStorageMemoryWith` configure it.

The encrypted server serves the new `EventLogMessage.EventLogCompactionRpcs` group (status, begin, input, fetch, part, abort and commit) when its `Storage` provides `compaction`, and sets the new `HelloResponse.compaction` flag. The server applies the compaction policy: the lag and threshold trigger with multiplicative no-op backoff, per-connection joining and validation of uploaded segments, the commit checks, and virtual sequence assignment for snapshot batches. Every request checks that its identity is authenticated on the connection and that the stage belongs to the store. Commits and rollbacks are logged. Writes no longer acknowledge re-uploaded entries first stored at or below the active snapshot base. `EventLogServer.layerRpcHandlers` takes a `compaction` option that sets `HelloResponse.compaction`.

`SqlEventLogServerEncrypted` storage always provides `compaction` on PostgreSQL, MySQL, SQL Server and SQLite. `makeStorage`, `layerStorage` and `layerStorageSubtle` take the same `compaction` options. The compaction tables are created on startup and when a store is first opened. The batch and entry id tables are unchanged. The first instance to open a store that predates the upgrade makes its existing data compactable after the lag. Writes take sequences under a per-store row lock, so sequences stay increasing during a rolling deploy and after pruning has emptied a store's batch table. A sweep in the storage's scope prunes superseded generations after the grace period. Sweepers claim a store with a lease, and the next sweep finishes a prune that stopped part way.

`EventLogRemote` gains an optional `compaction` member, present when the server sets `HelloResponse.compaction` and the RPC client includes `EventLogCompactionRpcs`. It reads the compaction status, opens a stage, streams the stage's input headers, fetches and decrypts input batches, uploads kept entries, and commits or aborts the stage. Uploads pack the kept entries into batches, encrypt them, and send them in segments of about 512 KB, splitting an oversized segment into pieces and resending a whole segment after a dropped connection. `EventLogRemoteClient` takes the compaction RPCs as optional methods, and its `layer` builds the client from both RPC groups. `layerEncryptedWith` and `makeEncryptedWith` take a `compaction` option: `false` marks the remote's `compaction` member as opted out, so the client doesn't poll the status or run compaction.

`EventLog` runs encrypted remote compaction. A client with a `remote: true` compactor whose remote offers compaction and hasn't opted out polls the compaction status on each connect and about hourly, and starts a background run after a random delay when the server wants compaction and its journal has caught up. Other clients never call the compaction RPCs. A run reads the input headers, takes entries the journal already holds and fetches the rest, folds the opted-in compactors over the input, and reports a no-op or uploads and commits the kept entries. It aborts its stage, uploading nothing, when the idempotence check fails, a compactor dies or the input is pruned. The server's busy claim keeps a second run on the same store from starting. The new `EventLog.compact` runs one compaction now, without the caught-up check, and returns each remote's result. `Registry` gains `remotes`, the registered remotes by id.
